// quickstart

Getting started

Download a native build for desktop platforms or try it directly in your browser via WebAssembly. It includes the open-source AROS ROM, allowing you to test configurations immediately without needing your own Kickstart files.

  1. 1

    Download or install

    Grab pre-built packages for macOS, Linux, and Windows from the downloads section, or install with Homebrew.

  2. 2

    Launch

    Run Copperline to open the configuration GUI, or launch from the terminal to boot the built-in AROS Kickstart replacement.

  3. 3

    Load software

    Insert disk images (ADF, IPF, etc.) via the status bar or pass files on the command line: copperline game.adf. WHDLoad archives can also be launched directly: copperline --whdload game.lha.

Standard Commodore Kickstart ROMs (1.3, 2.05, 3.1) and custom ROMs like DiagROM are fully supported. Simply select your ROM in the launcher or pass it on the command line.

// features

Features and architecture

Accurate chip-level emulation validated against test suites, custom test disks, and real hardware, combined with rich inspection and debugging tools.

timing core

Cycle-level chip bus

Chip bus arbitration is scheduled per colour clock across the CPU, Copper, blitter, and DMA channels (display, sprite, audio, disk, and refresh), with hardware bus sequencing and modelled interrupt latency.

chipsets

OCS, ECS & AGA

Configurable Agnus and Denise/Lisa revisions covering the A1000, A500, A500+, A600, A1200, A3000, A4000, CDTV, and CD32. Supports Kickstart 1.2 through 3.1, DiagROM, and the bundled AROS ROMs.

cpu

68000 through 68060

Configurable 68000 to 68060 CPU models with accurate 68000 cycle counts, MMU support (030/040/060), on-chip caches, 68060 dual-issue execution, and 68881/68882 FPU emulation. An experimental JIT compiler is available for fast 68020+ execution.

peripherals

Audio and input

Four-channel Paula audio with the hardware low-pass filter, plus Toccata sound cards and MHI MP3 decoders. Built-in MIDI routing supporting host MIDI, emulated Roland MT-32, and Coppersynth (SoundFont GM synth). Full input support for mice, joysticks, CD32 pads, and USB gamepads.

storage

Storage and media

Up to four floppy drives supporting ADF, ADZ, DMS, IPF, and SCP formats, plus real floppy drives via Greaseweazle. Hard disk and CD-ROM support via Gayle IDE, A4000 IDE, Zorro IDE, and A2091/A3000/A4091 SCSI. Mount host directories as bootable AmigaDOS volumes or attach physical host drives.

expansion

Pluggable Zorro boards

Zorro II and III autoconfig expansion architecture with support for external WebAssembly plugin cards. Community or custom boards can implement memory mapping, DMA, interrupts, and I/O alongside built-in cards.

networking

Ethernet and networking

Commodore A2065 Ethernet emulation supporting user-mode NAT with DHCP (no host root/driver required) or direct bridging to host network adapters. Includes a HostSocket expansion board for direct bsdsocket.library integration without a guest TCP/IP stack, and serial-over-TCP/telnet support.

rtg

RTG graphics

High-colour Workbench and RTG display modes via Zorro III (Z3660) and Zorro II (Picasso II / II+ and Graffity) graphics cards. Supports 8, 16, and 32-bit colour depths with accelerated blits and Picasso96 driver compatibility.

graphics

Video and display path

Accurate OCS, ECS, and AGA video pipelines: bitplanes (up to 8 in AGA), HAM6/HAM8, Extra Half-Brite (EHB), dual playfield, hardware sprites, and collision registers, all rendered in sync with the raster beam.

presentation

CRT shaders and display

Customisable video presentation with CRT shaders (scanlines, shadow mask, CRT curvature), custom WGSL shaders, integer scaling, aspect ratio correction, and deinterlacing for laced screens. Includes optional monitor bezels with reactive LEDs and amber/green/sepia monochrome screen tints.

tooling

Debugging and reproducibility

Built-in reverse-stepping CPU and Copper debugger, GDB-compatible console interface, chip-bus frame analyzer, deterministic state recording and playback (.clscript), and JSON-RPC control protocol for automated testing and scripting.

Hardware status at a glance

// configuration

Graphical machine launcher

Configure hardware profiles, CPU models, memory expansions, and storage devices directly in the GUI. Configurations can be saved to and loaded from standard TOML configuration files.

machine configuration

Complete hardware configuration

Easily select base machine profiles (from the Amiga 1000 through the 4000 and CD32) and adjust CPU models, memory allocations (Chip, Fast, Slow, Zorro III), Kickstart ROMs, storage controllers, and display settings.

The GUI automatically reflects options exposed by external WASM plugin boards and synchronises with TOML configuration files for easy sharing and command-line use.

  • Profiles Start from standard presets (A1000, A500, A600, A1200, A3000, A4000, CDTV, CD32) and customise as needed.
  • Chipset & CPU Select CPU models (68000-68060), clock speeds, FPU, MMU, caches, and chipset revisions.
  • Memory & ROM Configure Chip, Slow, Fast, and Zorro III RAM, alongside Kickstart and extended ROM images.
  • Storage Manage floppy images and swap playlists, IDE/SCSI hard disks, CD images, and host directory shares.
  • Zorro & plugins Manage autoconfig expansion boards, WASM plugin cards, and A2065 network adapters.
  • A/V & display Configure CRT shaders, aspect ratios, scaling options, audio filters, and volume levels.
// debugger

Interactive and reverse debugging

Pause emulation at any time (Cmd+B / Ctrl+B) to inspect CPU registers, custom chipset state, memory, the Copper list, and audio channels. A dedicated GDB-style console (Cmd+K / Ctrl+K) is available for command-driven debugging.

reverse debugging

Step backwards in time

Tracking down memory corruption or timing glitches often requires finding which instruction or DMA cycle caused the issue. Copperline maintains a rolling buffer of deterministic state snapshots, allowing you to step, run, or rewind backwards across frames.

Because the core is fully deterministic, rewinding and replaying execution produces consistent, cycle-identical results every time.

  • < Step Step one instruction backward
  • < Frame Rewind to the previous video frame
  • < Run Reverse execution to the previous breakpoint

Also includes automated reverse watchpoints for tracking the last writer to any memory location. See the reverse debugging documentation.

  • CPU View and edit registers, inspect status flags, and follow live disassembly at the Program Counter.
  • Chipset Inspect custom register states (DMACON, INTENA, INTREQ), Copper state, and beam counters.
  • Copper Disassemble active Copper lists with support for breakpoints and single-stepping.
  • Video Isolate or hide individual bitplanes and sprites to diagnose rendering issues, and view the active palette.
  • Audio Monitor DMA state machines, pointers, and live waveforms across all four Paula channels and CD-DA.
  • Memory Hex and ASCII memory editor with search, file export, memory editing, and write-tracking watchpoints.
  • IO Map Complete custom register map with live values and decoded bitfields.
  • Break Set conditional PC breakpoints, memory watchpoints, and custom register access traps.
// frame analyzer

Chip bus frame analyzer

The built-in frame analyzer visualises bus activity across an entire video frame, mapping every colour clock and scanline to the active bus master.

chip-bus arbitration

Visualising DMA and bus contention

In the Amiga architecture, the CPU, Copper, blitter, and DMA channels all share access to chip RAM. The frame analyzer charts bus allocation across the entire display frame, making DMA contention, CPU starvation, and blitter stalls immediately visible.

Inspect individual cycles to view exact beam positions, owners, and blitter operations, or evaluate overall bus usage breakdowns across the frame.

  • Frame underlay Overlay bus activity maps directly on top of the rendered frame to correlate DMA activity with visual elements.
  • Register markers View exactly where custom register writes occurred relative to the raster beam.
// headless & automation

Scriptable and deterministic

The emulation core is deterministic: unthrottled headless runs produce identical results to interactive windowed sessions given the same inputs and media. This makes Copperline well suited for regression testing, scripted capture, and automated benchmarking.

  • Command-line control: Configure machine profiles, CPU models, memory allocations, and storage attachments directly via CLI arguments without a config file.
  • Scripted input and capture: Inject keystrokes, mouse movement, and joystick inputs on precise frame schedules, outputting screenshots, raw frame dumps, WAV audio, or save states.
  • Session recording and replay: Record user inputs to a .clscript file and replay sessions deterministically for bug reports and regression tests.
  • Self-contained save states: Save states encapsulate the full machine state and can be restored even without the original ROM file present.
  • JSON-RPC control protocol: Drive live sessions over a loopback TCP socket (--control) to manage breakpoints, inject input, swap media, and stream frame, serial, or interrupt events.
  • Automated testing and CI: Run headless benchmarks and automated test suites in CI environments without requiring a window server or GUI.
scripted capture
# boot a disk, press space after 4s, save a screenshot at 12s (headless)
copperline game.adf --noaudio \
  --press-after 4 SPACE \
  --screenshot-after 12 shot.png

# record an input session, then replay it to render audio to WAV
copperline game.adf --record-input run.clscript
copperline game.adf --script run.clscript --audio-wav run.wav

// project status

Current development status

Copperline is under active development. Below is an overview of what is currently well-tested, recent additions, and known areas for future work.

Working well

  • OCS, ECS, and AGA display pipeline, including HAM6/HAM8, EHB, dual playfield, and beam-synchronized rendering.
  • Cycle-accurate 68000 CPU emulation (SingleStepTests verified) and 68020-68060 support with FPU and MMU.
  • Deterministic session recording, save states, and reverse-stepping debugger.
  • Inspection tooling: CPU/chipset debugger, memory editor, and chip-bus frame analyzer.
  • Standard floppy formats (ADF, ADZ, DMS, IPF, SCP), Gayle and A4000 IDE, SCSI controllers, and bootable host directory mounts.

Recent additions

  • Coppersynth SoundFont synth, Toccata audio, and MHI MP3 decoder boards.
  • Physical floppy drive support using the FluxBridge library with Greaseweazle hardware.
  • RTG graphics (Z3660, Picasso II/II+, Graffity) across 24-bit and 32-bit machine profiles.
  • A2065 Ethernet network bridging (user-mode NAT and host interface bridging).
  • Experimental JIT compilation mode for 68020+ CPUs.
  • WebAssembly browser build.

Not yet implemented

  • High-density (1.76 MB) and PC/CrossDOS floppy disk formats.
  • Non-QWERTY host keyboard layout mappings.
  • Additional physical floppy controller interfaces beyond Greaseweazle.

or install with homebrew

run the windows build

// faq

Frequently asked questions

Do I need a Kickstart ROM?

No. Copperline bundles the open-source AROS boot ROM, which allows many programs and homebrew software to run out of the box. However, commercial games and standard Workbench installations typically require genuine Commodore Kickstart ROMs. You can use ROMs dumped from your own Amiga hardware or acquired through licensed packages like Cloanto's Amiga Forever.

Why isn't the macOS build notarized?

Copperline is an open-source project maintained in free time, and binaries are currently ad-hoc signed rather than notarized through an Apple Developer account. On first launch, macOS Gatekeeper may ask you to confirm opening the app under System Settings > Privacy & Security. Alternatively, installing via Homebrew builds from source on your machine.

How does Copperline compare to established emulators like WinUAE, FS-UAE, or vAmiga?

WinUAE, FS-UAE, and vAmiga are mature projects with extensive compatibility across the vast Amiga software library. Copperline focuses particularly on developer and debugging tooling: cycle-by-cycle chip bus analysis, deterministic reverse debugging and rewind, headless automation and scripting, and a modern Rust codebase designed for extensibility and embedded WebAssembly use.

Will my software or game run?

Many popular games, demos, and Workbench setups run well, and compatibility is continuously expanding. Since Copperline aims to accurately model hardware rather than applying per-title game patches, fixes directly improve overall fidelity. If you encounter an incompatibility, recording a session with --record-input produces a reproducible .clscript file that can be attached to a GitHub issue for debugging.

How was Copperline developed?

Copperline was developed by Andrew Hutchings (LinuxJedi) in Rust, drawing on hardware documentation, reference machines, and test disks run on real Amiga hardware. AI coding assistants and agents were utilized during development to assist with implementation, test generation, and automated debugging workflows. Accuracy is validated against hardware test suites and published regression benchmarks.

Where does the name come from?

The name refers to the Amiga's Copper coprocessor, which executes instructions synchronized to the display beam to create the iconic raster bar color gradients seen throughout classic Amiga demos and games.

// about the author

Why Copperline exists

Copperline started from a desire for an Amiga emulator that was both simple to automate from the command line and equipped with powerful debugging tools. The initial milestone was booting DiagROM far enough to display its menu.

Over time, the project expanded into a full emulation suite focused on developer productivity: a debugger that can step backwards, cycle-accurate bus analysis to diagnose DMA contention, and deterministic recording so bugs can be reproduced reliably.

When not writing Rust, I spend much of my time working on real Amiga hardware: repairing, collecting, and designing expansion boards. Having physical machines on the workbench provides a direct reference to ensure the emulation matches real-world behaviour.

- Andrew Hutchings (LinuxJedi) · linuxjedi.co.uk · GitHub
